# 검증

루트 [AGENTS.md](../AGENTS.md)를 먼저 읽고 변경과 관련된 검증을 선택한다.

- 대상 파일과 빌드 구성, 작업 디렉터리, 실행 명령, 기대 결과를 먼저 확인한다.
- 프로젝트 이동은 `.sln` 경로, GUID, `.vcxproj` 항목의 실제 존재, 필터와 물리 디렉터리 일치, 이전 경로 잔존 여부를 확인한다.
- C++ 빌드 설정 변경 시 Debug/Release × Win32/x64를 검증한다. 전체 솔루션은 C# 도구의 빌드도 확인한다.
- 기능 변경은 정상·실패·경계 중 해당 범위를 검증한다. 실제 데이터나 실행 조건이 없으면 그 한계를 기록한다.
- 기존 검증을 우선 사용한다. 같은 소스·환경에서 성공한 검증은 새로운 변경이나 미해결 문제가 없으면 반복하지 않는다.
- 기존 결함과 변경으로 생긴 결함, 환경/의존성 실패를 구분한다. 실제 명령과 결과를 근거로 통과·실패·미실행을 보고한다.

## 증분 검증과 한 번의 마감

1. 수정 전 허용 경로/담당자, 보호 입력, 보존할 기존 assertion·실패 진단·롤백·fault-hit 조건, 필요한 최종 gate를 현재 작업 기록에 짧게 고정한다. 기록용 새 runner/일회용 검증 스크립트를 만들지 않는다.
2. 기존 `Tools/Tests` 진입점과 `native_build.py`/`NativeTests.vcxproj`를 재사용한다. 원본 소스를 직접 빌드하고 구성·아키텍처·suite·분석 모드·생성 헤더 variant별 고정 obj/PCH 캐시를 유지한다. `Build`를 기본으로 하며 `Clean/Rebuild`나 매 실행 새 소스 복사 빌드는 하지 않는다. 공유 GameData/Packer/Store/예외 테스트도 승인된 타깃별 PCH를 사용한다. 안정 std/SDK만 공유하고 compiled PCH는 구성·타깃·아키텍처·분석별로 격리한다. 치환 매크로·reader 정의·직접 포함 CPP는 PCH 뒤에 둔다. 기본 인수 추가 시 macro 치환 wrapper까지 기존 API 소비자로 조사한다.
3. XML·프로젝트/필터 변경 직후에는 양쪽 XML 파싱, 실제 경로·중복·등록 일치를 기존 `python Tools/Tests/test_input_build_contract.py`로 먼저 확인한다. 데이터/아트 변경이면 기존 데이터 검사에서 ID·규격뿐 아니라 승인 원시 바이트 등 더 강한 불변식도 보존한다. 정확한 진단 문자열/위치는 실제 최소 양성·음성 fixture에서 먼저 확인한다. 한 x64 실제 동작이 정상임을 확인하기 전에 같은 오류를 네 구성에 배포하지 않는다.
4. Worker는 변경 경로/해시·실제 명령/결과·남은 차단 사항·소유권 해제를 함께 인계한다. 부모는 이를 한 번에 대조하고 즉시 통합하며 임의 정리/검사 확장으로 인계를 지연하지 않는다. 비싼 최종 matrix는 한 담당자만 실행한다. 이미 확인된 같은 구성은 해시/의존성/결과가 동일할 때 승계하고 누락된 구성만 추가한다.
5. 성능 개선 완료에는 실제 cold, 변경 없는 warm, 소스 한 파일 및 의존 헤더 변경 시의 부분 재빌드 증거가 필요하다. protected 원본의 바이트는 바꾸지 않고 mtime 의존성 시험을 쓸 경우 원래 값을 복구하며, 다른 작업자와 빌드가 겹치지 않게 한다. 컴파일 obj 수·PCH 재생성·분석 실제 실행을 구분해 기록한다.
6. 최종 후보를 고정한 뒤 독립 검토한다. 테스트/문서만 보완했으면 변경 없는 C++/생성물/최종 EXE 해시와 기존 통과 기록을 확인해 불필요한 재컴파일을 피한다. 초기 FAIL과 실제 새 집중 검토 범위는 보존·구분한다.
7. 원시 결과 배열·개수·경고·소스/산출물 해시·독립 검토를 하나의 최종 수용 기록으로 집계한 뒤 README/로드맵·task 상태·완료 보고를 묶어서 갱신한다. 집계/표현 수정 때문에 테스트를 다시 돌리지 않는다. 필수 경고 0·회귀·원본 보호 기준을 낮추는 절차가 아니며 첫 수정의 무결함을 보장한다고 주장하지 않는다.
