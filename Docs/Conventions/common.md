# 공통 코딩 컨벤션

프로젝트 소유 코드에 적용한다. C++ 작업은 [cpp.md](cpp.md)를 함께 읽는다. C# 개발 도구에는 기존 C# 스타일과 프로젝트 계약을 유지한다.

## 파일·명명
- UTF-8, 신규 텍스트 파일은 LF를 기본으로 한다. Visual Studio 등 도구 필수 예외를 허용하며 기존 파일의 전체 개행/포맷 변경을 기능 수정과 섞지 않는다.
- 식별자와 파일명은 영어, 주석은 한국어로 작성한다. 단위는 `elapsedMilliseconds`, `fileBytes`처럼 이름에 표시한다.
- bool은 상태/질문형으로 명명하고 의미 없는 축약을 피한다. 함수는 한 책임에 집중하며 숨은 I/O와 가변 전역 상태를 피한다.
- 외부 라이브러리는 기존 계약/스타일을 유지한다. 생성물은 원본 또는 생성기를 수정한다.

## 계약·오류·데이터
- API의 입력 조건, 소유권, 유효 수명, 실패 결과를 명확히 한다. 가변 상태의 소유자와 변경 위치를 정한다.
- Excel 데이터의 모든 PK·FK는 숫자 정수다. item_id/skill_id뿐 아니라 현지화·Scene·아트·진행 참조에도 적용하며 문자열·이름·경로를 데이터 키로 쓰지 않는다. [Excel 작성 규칙](../../GameData/Excel/README.md)에 맞춰 원본·생성기·런타임·검사를 함께 유지한다.
- 예상 가능한 실패는 결과로 구분한다. 빈 catch, 무조건 재시도, 부분 실패 은폐를 금지한다.
- 입력과 파일 경계에서 길이·범위·형식·상태를 검증한다. 로그에는 원인과 위치를 남기고 민감정보를 제외한다.
- 저장·생성 작업은 기존 데이터 보호, 실패 시 상태, 재실행 가능성을 확인한다. 구현하지 않은 저장 기능을 미리 추가하지 않는다.

## 주석·검토
- 주석은 이유, 불변식, 수명을 설명한다. 임시 우회에는 제거 조건을 남긴다.
- 합의한 계약과 구현이 다르면 원인을 판단한 뒤 필요한 내용을 함께 수정한다. 문서만 바꿔 불일치를 숨기지 않는다.
- 정상·실패·경계 사례 중 변경과 관련된 범위를 검증하고 실제 검증과 미검증을 구분한다.
- 파일 배치와 Visual Studio 필터 정책은 루트 [AGENTS.md](../../AGENTS.md)를 따른다.

## 커밋 메시지

### 기본 태그

커밋 제목은 `[태그] 작업 내용` 형식으로 작성한다. 콘텐츠 개발은 큰 작업 이름과 이번 커밋의 세부 변경을 함께 적는다.

| 태그 | 용도 | 제목 예시 |
|---|---|---|
| `[콘텐츠]` | 전투·상점 등 큰 콘텐츠 단위의 기능 개발 | `[콘텐츠] 전투 시스템 개발 - 피해량 계산 구현 #1` |
| `[개선]` | 구조·가독성·성능 등 기존 코드 개선. 무엇을 어떻게 개선했는지 명시 | `[개선] 데이터 로딩 - 중복 검증 로직 공통화` |
| `[수정]` | 정상 동작하지 않던 기능·오류를 고치는 버그 수정. 일반 코드 개선과 구분 | `[수정] 저장 실패 시 기존 세이브 보존` |
| `[문서]` | 기획·설계·계획 문서, README, 툴 사용법 작성·수정 | `[문서] GameDataGenerator 사용법 작성` |
| `[리소스]` | TextArt 등 게임 리소스 추가·교체·정리 | `[리소스] 몬스터 TextArt 추가 - 슬라임` |

콘텐츠 제목의 기본 형식은 다음과 같다.

```text
[콘텐츠] 큰 콘텐츠 작업 - 이번에 개발한 세부 내용 #번호
```

- 같은 콘텐츠를 이어 개발할 때 큰 작업 이름은 유지하고 세부 내용으로 이번 변경을 구분한다.
- `#번호`는 **콘텐츠별 작업 순번**이다. 새 콘텐츠는 `#1`부터 시작하고 같은 콘텐츠의 다음 작업은 `#2`, `#3`처럼 이어 간다. 다른 콘텐츠의 번호와는 별도로 관리하며 GitHub 이슈 번호를 뜻하지 않는다.

```text
[콘텐츠] 전투 시스템 개발 - 피해량 계산 구현 #1
[콘텐츠] 전투 시스템 개발 - 턴 진행 구현 #2
[콘텐츠] 상점 시스템 개발 - 상품 목록 구현 #1
```

- 제목은 실제 변경을 요약한다. `작업`, `수정함`처럼 대상과 내용을 알 수 없는 제목은 피한다.
- 관련 없는 콘텐츠·코드 개선·문서는 가능하면 별도 커밋으로 나눈다. 한 변경에 필요한 코드·데이터·테스트·문서는 주된 목적의 태그로 함께 묶을 수 있다.
- 이 규칙을 문서화하는 것은 커밋·스테이징·푸시 권한을 뜻하지 않는다. 실제 Git 작업은 별도 요청 범위에서만 수행한다.

### 추가 태그 제안 — 아직 기본 규칙으로 확정하지 않음

| 태그 | 분리하면 유용한 경우 | 제목 예시 |
|---|---|---|
| `[빌드]` | 프로젝트·링크·패키징·의존성·CI 등 빌드 구성 변경 | `[빌드] GameData 정적 라이브러리 참조 경로 정리` |
| `[테스트]` | 제품 기능 변경 없이 회귀 테스트·검증 도구를 추가하거나 보완 | `[테스트] 손상된 세이브 거부 회귀 추가` |

기본 태그는 `[콘텐츠]`·`[개선]`·`[수정]`·`[문서]`·`[리소스]`로 확정한다. `[빌드]`·`[테스트]`는 별도로 이력을 구분할 필요가 있을 때 도입한다.
