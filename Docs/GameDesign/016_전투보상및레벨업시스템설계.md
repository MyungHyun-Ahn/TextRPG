# 전투 보상·경험치·레벨업 시스템 설계

> 상태: **로컬 구현·실행·독립 소스 검토 완료 — 2026-11-20**. 구현 전 기준은 `45f80fc`다. 사용자 전체 구현 승인 이후의 실제 계약을 기록하며 커밋·원격 게시 여부는 별도로 확인한다.
> 사용자 확정: 몬스터 골드는 Min/Max 범위 지급, 재화는 Enum으로 구분하여 Gold부터 활성화하고 다이아·루비 등에 확장한다. **확장성을 최우선**으로 한다.
> [015](015_기본스탯및턴제전투1차구현설계.md)의 기본 공격 사이클을 확장한다. 015의 보상 미구현 표시는 당시 1차 범위의 이력으로 유지한다.

## 1. 목표와 범위

`전투 승리 → 범위 재화·경험치 정산 → 다중 레벨업 → 결과 확인 → 저장·재개 → 마을 복귀 → 강화된 상태로 재전투`를 연결한다.

- 구현: Gold만 활성화한 재화 Enum, 타입별 잔액, Min/Max 재화 보상, 고정 경험치, 누적 XP·자동 레벨업, 능력치 재계산, 결과 영수증, 저장·복원·중복 방지.
- 제외: 아이템 드롭, 가중치/확률 드롭, 보상 선택·수령 버튼, 장비, 스탯 포인트, 스킬/코스트/상태 이상, 업적·일일·계정 보상, 범용 보상 큐, 외부 거래 원장.
- UI가 지급하거나 전역 RewardManager가 진행을 중복 소유하지 않는다. 게임 수치·초기값·표시 문구는 Excel 원본이다.

| 항목 | 구현 계약 |
|---|---|
| 지급 대상/시점 | 정상 승리만 최종 타격의 동일 게시에서 지급. 패배는 지급·보상 추첨 없음 |

최초 제안 이후 이 정책 전체를 사용자 구현 승인에 따라 연결했다. 유료 결제·환전·재화별 상업 정책은 포함하지 않는다.

## 4. Excel·생성기·Store 계약

### 4.1 Combat.xlsx / MonsterDefinition

기존 MonsterId를 유지하고 다음 네 필드를 사용한다.

| 필드 | 타입/기술 범위 | 의미 |
|---|---|---|
| RewardExperience | 필수 Client uint32, 0..1,000,000 | 승리 예정 경험치 |
| RewardCurrencyType | 필수 Client ECurrencyType | 지급 타입. 운영 원본은 Gold |
| RewardAmountMin | 필수 Client uint32, 0..1,000,000 | 포함 최소 추첨량 |
| RewardAmountMax | 필수 Client uint32, 0..1,000,000 | 포함 최대 추첨량 |

Generator와 Store 모두 `0 <= Min <= Max`를 검사한다. Min=Max와 0/0은 정상이며 Min>Max를 자동 교환하지 않는다. 현재 몬스터당 재화 한 종류다. 후속 타입은 같은 필드·공통 처리로 지급하며 GoldMin/DiamondMin/RubyMin 같은 열·지급 분기를 늘리지 않는다. 복수 동시 지급 정의가 필요해지면 행 목록으로 확장한다. 경험치는 재화 Enum이 아니라 성장 도메인이다.

닫힌 필드·Client-visible scope·양수 HP·PK/FK·SceneType·아트 역할·현지화 참조를 producer/Store에서 검사한다. 진행 cohort의 완전 부재와 부분 부재를 구분하며, 불량 원본의 정확한 진단과 양쪽 출력 보존을 유지한다.

### 4.2 InGameData.xlsx / LevelDefinition

- RequiredExperience는 해당 레벨 도달에 필요한 **누적 총경험치**다.
- Level은 1부터 연속·유일, 첫 문턱 0, 이후 문턱 엄격 증가다. 임의 재번호는 하지 않는다.
- MaxHp/Attack/Defense는 레벨별 **절대 기준값**이며 비감소를 요구한다. 이전 행들을 합산하지 않는다.
- 초기 profile의 Level/XP 구간, 타입·범위·참조를 검증한다.
- 끝에 레벨을 추가하는 호환과 기존 문턱 변경·삭제·하향 재밸런싱을 구분한다. 후자는 별도 콘텐츠 이관이다.
- 저장 가능한 곡선 witness는 Core codec의 **4096원소 기술 한도** 안이어야 한다. Store가 더 큰 정적 표를 읽더라도 NewGame/Continue 후보 성공 전에 저장 불가능한 진행을 거부한다. 이는 두 번째 게임 성장 상한이나 Excel 수치 원본이 아니다.

### 4.3 재화 Enum과 단일 잔액

- Excel 생성 `GameData::Common::ECurrencyType : uint32`, 운영 `Gold = 1`만 등록한다. 0/미등록 값은 거부한다.
- Diamond/Ruby는 확장 예시다. 활성화 시 새 안정 숫자 ID를 부여하고 Gold ID를 변경·재사용하지 않는다.
- 루트 `m_currencies: vector<SCurrencyBalance>`의 `CurrencyType + Amount`가 유일한 잔액이다. 문자열·배열 위치로 저장하지 않는다.
- `GetCurrency(ECurrencyType)` / `SetCurrency(ECurrencyType, ...)`가 공통 경로다. GetGold/SetGold는 호환 래퍼이며 별도 m_gold 원본은 없다.
- 중복·0·미등록 타입은 거부한다. 등록 타입의 항목 부재는 잔액0으로 조회하고 저장 순서는 숫자 타입으로 정규화한다.
- 기존 NewGameProfile.initialGold는 Gold 초기 항목 입력이다. 다른 타입 초기값·게임상 한도는 임의 추가하지 않았다.
- 운영 원본을 바꾸지 않는 추가 Enum fixture로 독립 잔액·동일 지급·숫자 wire 복원을 검사했다. 운영 UI는 아직 Gold만 표시한다.

## 5. 누적 경험치·포화 지급

`T(L)`은 레벨 문턱, `M`은 마지막 레벨이다.

```text
XP 여유 = 기존 XP >= T(M) 이면 0, 아니면 T(M) - 기존 XP
실제 경험치 = min(예정 경험치, XP 여유)
새 누적 XP = 기존 XP + 실제 경험치
새 Level = 새 누적 XP가 도달한 가장 높은 레벨
```

계산과 영수증 검증은 ExperienceGrant / ExperienceLevel의 같은 경계를 사용한다. Level과 XP를 따로 게시하지 않는다. 중간값은 넓은 정수로 처리하고 도달한 최종 레벨을 찾는다. XP0 승리도 정상이다. 기존 초과 XP를 버리거나 최신 곡선으로 과거 지급량을 재작성하지 않는다. XP 진행 표시는 문턱 차이로 재생성하고 저장하지 않는다.

설명/회귀 예: 문턱 0/100/250/450에서 XP80에 300 지급이면 XP380/Level3이다. XP430에 80 예정이면 실제20/미적립60이다. 초기 플레이 XP는 별도 Excel profile을 따른다.

재화는 snapshot 범위에서 한 번 추첨한 뒤 `min(추첨량, UINT32_MAX - 해당 타입 잔액)`을 지급한다. 잔액 여유로 추첨 범위를 줄이거나 포화됐다고 재추첨하지 않는다. 다른 타입 잔액은 불변이다.

## 6. 능력치·HP

```text
HP/기본 공격/기본 방어 = LevelDefinition 절대값 + 기존 StatBonuses
주 능력치 입력 = CharacterCombat 정의 + 기존 m_basicBonuses
전투 능력치 = 위 입력과 CombatRule의 계수/방어/스피드/치명타 계산
```

- 새 레벨 기준값을 StatBonuses에 다시 적립하거나 기존 보너스를 버리지 않는다.
- 큰 합산·최종 공격/방어/스피드는 마지막 투영에서 uint32 표현 상한으로 제한한다. 원본·CombatRule·참조 검증은 유지한다.
- 현재 HP·원본 증가분은 저장하지만 MaxHp·최종 전투 스탯 캐시는 저장하지 않는다.
- 승급 HP는 `min(새 MaxHp, 전투 직후 HP + max(0, 새 MaxHp - 이전 MaxHp))`다. 여러 레벨도 최종 증가분을 한 번 적용한다.
- 기존 healOnReturn과 승급 보충은 별개다. 로드의 레벨 이관은 HP를 보충하지 않는다.
- 네 주 능력치의 자동 레벨 성장·스탯 포인트는 추가하지 않았다.

## 7. 전투당 한 번 정산·역사적 영수증

`SBattleProgress.Reward`는 생성형 SBattleRewardProgress 값이다. 진입 때 몬스터 예정 XP와 재화 snapshot을 고정한다.

| 필드 | 의미 |
|---|---|
| State | 0=전투 없음, 1=준비, 2=정산 완료, 3=구전투 제외 |
| PlannedExperience / GrantedExperience | 진입 예정량 / 실제 반영량 |
| Currencies | `vector<SCurrencyRewardProgress>`: 타입·Min/Max·RolledAmount·GrantedAmount |
| LevelBefore / LevelAfter | 정산 당시 레벨. 현재 레벨의 두 번째 원본 아님 |
| ExperienceBefore / ExperienceAfter | 정산 전/후 XP 사실. since5 |
| CurveMaxLevel | 당시 계산에 사용한 역사적 곡선 prefix. since5 |
| CurrencySeed / CurrencyRandCount | 별도 보상 RNG의 uint64 seed / 실제 raw 출력 count |

진입은 Prepared+Active, 승리는 Victory+Settled+보상/성장의 동일 게시, 패배는 Defeat+Settled+지급0이다. 귀환은 전투·영수증을 함께 비운다. schema1/2/3 구전투는 LegacyExcluded로 신규 지급하지 않는다.

- 상태·타입·범위·레벨·XP 관계를 검증한다. 전투 없음/LegacyExcluded는 빈 영수증이다.
- XP 영수증은 당시 prefix의 포화 지급식과 도달 레벨로 검사한다. 역산 XP의 직전 레벨 구간 검사만으로 잘못된 부분 지급을 수용하지 않는다.
- 완료 승리의 재화는 **읽기 전용 지역 Selector(seed,0)**로 저장 순서·범위를 재현하여 모든 roll과 최종 raw count를 비교한다. 현재 wallet·활성 RNG를 바꾸거나 보상을 재적용하지 않는다.
- Min=Max는 RNG 무소비다. 비고정 범위는 rejection의 버린 출력까지 raw count에 포함한다. FSelector::SelectRange를 사용하며 modulo 편향·값별 가중치 나열·일반 Restore의 임의 count 상한을 추가하지 않는다.
- Render/Continue/귀환/중복 입력/저장 재시도는 정산 트리거가 아니다. 과거 파일 롤백 방지는 보장하지 않는다.

## 8. 원자적 게시·실패 보존

현재 불변식/Session 충돌 검사 → 지역 battle·깊은 캐릭터 사본·잔액 후보에서 타격/양 RNG 계산 → 종료 보상/성장/HP/영수증 준비 → 모든 할당·조회·전체 검증 → 콜백 없는 noexcept 대입/swap 게시 → Session 체크포인트 순서다.

거부/예외는 HP·레벨·XP·모든 잔액·라운드·양 seed/count·영수증·루트/캐릭터/컬렉션 참조·직렬화 바이트를 보존한다. 매 타격 루트 교체나 UI 소유 원본은 없다. 전환은 기존 EndFrame 결합 게시를 유지한다.

별도 FProgression/SProgressionChange 클래스·singleton은 만들지 않았다. 공통 성장 helper는 InGameData, 후보 정산은 FCombat, 행동·저장 조정은 Session, 표시는 UI 책임이다.

## 9. 체크포인트·재시도

- 기존 NewGame/정상 Quit 저장에 승패 종료 체크포인트를 연결했다. Continue 자체는 슬롯을 다시 쓰지 않는다.
- EGameActionResult는 Rejected / Applied / AppliedSaveFailed를 구분한다. 이미 적용한 보상을 재실행하지 않는다.
- 저장 실패 때 메모리·dirty/실패 안내를 유지하고 기존 비활성 슬롯을 저장 재시도로 사용한다. 네 슬롯·NoScroll·release gate는 유지한다.
- 재시도는 전체 Save만 수행한다. 성공한 전체 저장이 dirty 상태를 해제하며 Quit 저장 실패의 기존 오류 종료 의미는 유지한다.
- 마지막 정상 파일에는 종료·영수증·잔액·레벨이 함께 있다. 저장 전 강제 종료의 롤백 가능성과 디스크 무손실·외부 exactly-once는 구분한다.

## 10. 세이브·콘텐츠 호환

- 최종 writer는 **schema5**다. 재화/기본 영수증은 since4, root m_curveThresholds와 영수증 XP 전/후·CurveMaxLevel은 **since5**다. 구 필드 도입 버전을 소급 변경하지 않는다.
- schema1/2/3 m_gold는 Gold 잔액으로 그대로 이관한다. 초기 골드를 다시 더하지 않고 새 writer에 m_gold를 병행하지 않는다.
- schema1/2/3 구전투는 보상 제외다. schema4 유효 정산은 같은 포화/레벨 식을 만족하는 과거 prefix만 추론하여 이력·원 지급을 보존한다. 가능한 prefix가 없으면 거부한다. 여러 prefix가 맞을 때 실제 과거 상한의 유일 복원을 주장하지 않는다.
- schema5의 m_curveThresholds는 저장 당시 Excel 곡선 prefix의 **호환 근거**이지 현재 수치/MaxLevel의 두 번째 권위나 스탯 캐시가 아니다.
- 저장 prefix가 현재 Store 앞부분과 정확히 일치하고 저장 Level/XP가 그 prefix에서 유효해야 한다. 빈/미래/변경 prefix·손상된 현행 조합을 무조건 복구하지 않는다.
- 끝에 레벨을 추가하면 XP·HP·잔액·RNG·원 지급을 보존하고 현재 레벨만 이관한다. 과거 영수증 LevelAfter를 최신 레벨과 강제로 같게 하지 않는다.
- 과거 3레벨 문턱 0/100/250의 XP500이 새450을 넘는 active/settled/town 및 반복 Save/Load를 검사했다. 재지급·로드 회복은 없다.
- 당시 필드만 쓰는 독립 schema1/2/3/4 writer를 검사한다. 구버전 기본값과 현행 필수 필드 부재를 구분한다. 잔액 누락/중복/미등록·손상값·미래 형식은 출력/활성 상태/원 파일·키를 보존하며 거부한다.
- 저장 불가능한 곡선은 후보 성공 전에 거부한다. 4096 경계의 실제 인증 저장·복원과 4097 NewGame/Continue 거부를 검사했다.
- 필드 추가만으로 ContentVersion을 올리지 않았다. 레벨 삭제·기존 문턱 재배치·하향 재밸런싱은 별도 콘텐츠 이관이다.

## 11. UI·현지화

기존 HP/공격/방어/Gold에 레벨·XP 진행/MAX·실제 보상·미적립량·레벨 변화를 연결했다. Gold도 공통 타입 조회로 읽는다. 결과는 영수증 조회이며 UI 재생성·Continue에 재지급하지 않는다. 귀환 뒤 별도 영구 결과 이력 UI는 없다.

한국어·영어 라벨/안내는 기존 Excel Enums/Localization 원본이다. 비활성 후속 재화 슬롯은 추가하지 않았다. 원래 아트·시안·주석, 네 슬롯/NoScroll 및 프레임 끝 수명을 보존했다.

## 13. 최종 로컬 검증 기록

2026-11-20 기준 원본/PCH/고정 obj 캐시의 영향 검사와 불변 근거 승계로 마감했다. 체크포인트 그룹을 독립 단위 테스트 개수로 합산하지 않는다.

- Debug/Release × x64/Win32 solution Build·제품 분석 경고0, Scene 일반/분석, 모델 일반/분석 통과.
- 모델은 Debug 각265그룹, Release 각264그룹이다. Debug 전용 검사가 있는 차이를 숨기지 않는다.
- 네 구성 실제 앱의 기본 경로·보상/승급/귀환/재전투·별도 저장 재개를 검사하고 최종 게임 EXE SHA를 대조했다.
- 추가 재화, 선택 TextArt 헤더 부재 일반/분석, 불변 Core/Store/저장 서비스 근거를 유지했다.
- 최종 Release Generator DLL 검사본/원본 해시를 맞추고 self-test·실제 헤더 consumer·Scene contract를 검사했다. Enum의 기술 기호 literal만 구분하고 실제 행/표시 값 금지·음성 control을 유지한다.
- MSVC v145 seed_seq 첫4바이트 payload를 주입하며 Win32 8바이트/x64 16바이트 noexcept proxy는 제외한다. 양성 보정·정확 fault-hit/오류·참조/바이트 보존·회복을 확인했다. 지정 구현의 증거이지 보편적 OOM 복구 증명은 아니다.
- 52개 변경 코드·데이터·테스트 경로의 독립 전체/변경부 검토와 MSVC 의미 의존성 보충을 바이트 정체성으로 조합했다. 최초 FAIL·승인 차단·설정 실패는 삭제하거나 PASS로 덮지 않았다.
- 재현 진입점/옵션은 [테스트 사용법](../../Tools/Tests/README.md)을 따른다. CI·수동 호스트 시각 검증·외부 거래 exactly-once는 이번 결과로 주장하지 않는다.
