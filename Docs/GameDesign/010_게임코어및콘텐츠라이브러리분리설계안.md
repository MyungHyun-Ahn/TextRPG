# 게임 코어·콘텐츠 라이브러리 분리 설계

> 후속 SceneManager 추출 — **로컬 구현·검토 마감, 빈 출력 이슈는 사용자 승인 보류:** [013 §12](013_SceneManager공통기능및TextRPG로직분리계획.md#12-실제-로컬-구현과-검증-상태)에 실제 `TSceneManager<TAction>` 소유/전환 엔진과 `FTextRPGSceneManager` 상속, 네 구성 실행 범위 및 Debug/Win32 일반 앱의 미해결 빈 출력 실패를 기록했다. 아래 §10은 기존 라이브러리 분리 당시의 이력으로 보존한다. Core 콘텐츠 독립성 및 입력·진행·결합 게시 계약은 유지하며 후속 SCM-06은 이 예외를 명시하여 로컬 마감한다. 빈 출력은 재발 시 추적하며 원래 FAIL을 전체 검사 PASS로 바꾸지 않는다.

> 상태: **라이브러리 분리 완료 — 실제 링크·네 구성 실행·집중 독립 소스 검토 및 최종 수용 확인.** `GameData.lib`는 TextRPG 전용 정적 데이터 라이브러리이고 `ConsoleGameCore.lib`는 콘텐츠 독립 실행·입력·UI·렌더 기반이다. 최초 공용 GameData 기반 제안은 채택하지 않았다. 실제 구현/실행 범위와 최종 수용 상태는 아래 §10 및 로드맵 상단을 따른다.
> 적용 우선순위: 라이브러리 경계 및 공통 UI의 콘텐츠 의존성은 이 문서가 [007](007_Scene별UI객체및입력분리설계안.md)·[008](008_InputManager및SceneUILayer설계안.md)의 기존 FUIManager 연결 설명보다 우선한다. 기존 구현·검증 이력은 보존하며, [009](009_InGameData및저장복원설계안.md)의 진행 단일 소유·저장 보존·프레임 끝 수명 계약은 약화하지 않는다.

## 1. 확정한 목표와 비목표

- TextRPG 전용 생성 타입·Enum·타입별 Store·정적 콘텐츠 검증·패키지 처리를 `GameData.lib`로 묶는다. 범용 테이블 등록 프레임워크로 확장하지 않는다.
- 입력 상태, 콘솔 출력·FrameBuffer, 프레임 실행 순서, 공통 UI, 일반 Scene 수명 기반은 `ConsoleGameCore.lib`로 분리한다. Windows 전용 API를 사용할 수 있다.
- 구체 Scene·UI 조립, 게임 행동 해석, InGameData·FGameSession, NewGame/Continue 및 저장 시점은 TextRPG 콘텐츠에 둔다.
- 단순 프로젝트 항목 이동이 아니라 코어의 콘텐츠 타입 의존성을 제거한다. 인터페이스 이름만 바꾸고 StartGame/Attack·게임 데이터 접근을 그대로 노출하는 것은 분리가 아니다.
- 게임 동작·정적 Scene 세 필드·정확히 네 선택지·기존 ID/Enum 값·저장 포맷·키 정책은 변경하지 않는다. 코어 자체에 TextRPG의 네 선택지 수나 아트 슬롯 규격을 강제하지 않는다.
- 신규 전투·상점·설정, dirty 출력 최적화, 범용 저장 프레임워크, 다른 OS 지원, 신규 DLL은 이번 분리의 비목표다. `GameData.lib`와 배포 파일 `GameData.dat`는 서로 다른 산출물이다.

## 2. 분리 전 소스에서 확인한 결합 — 이력

아래는 분리 전 조사에서 확인한 결합과 수정 목표다. 삭제·이동된 원래 경로는 이력 표기이며 현재 구현은 §10의 경로와 계약을 따른다.

| 현재 위치 | 확인한 결합 | 목표에서의 처리 |
|---|---|---|
| `TextRPG/UI/FUIManager.h` (이동 전) | `Bind(FDataScene&)`, `GetBoundScene()`, `FDataScene*` 멤버 | 공통 UI API에서 구체 게임 Scene을 제거 |
| `TextRPG/UI/FUIManager.h` (이동 전) | `SUIOption`에 생성 `ESceneActionType`·TargetSceneId 포함 | 게임 선택지 바인딩 모델은 콘텐츠가 선언·소유 |
| `TextRPG/UI/FUIManager.cpp` (이동 전) | 생성 Enum 및 FDataScene 헤더 포함, 구체 Scene 입력·취소 호출 | 중립적인 UI 입력 대상 계약 또는 콘텐츠 연결기로 역할 분리 |
| [FDataScene.cpp](../../TextRPG/Scene/FDataScene.cpp) | SUIOption 생성·정렬·보관, bridge identity로 퇴장/복구 처리 | 게임 모델은 유지하되 정의 위치와 연결 경계를 정리하고 복구 보장을 보존 |
| [FUiTextArt.cpp](../../TextRPG/UI/Common/FUiTextArt.cpp) | 타입별 Store·생성 TextArt 행을 직접 조회 | 조회·디코딩은 데이터/콘텐츠 측, 코어 UI는 준비한 표시 자료를 수용 |
| [FSceneManager.h](https://github.com/MyungHyun-Ahn/TextRPG/blob/2782feb656713fde315926eb8a85d3ea11c10bf8/TextRPG/Scene/FSceneManager.h) | FGameDataStore·FDataScene·InGameData와 진행 소유 핸들 직접 사용 | 일반 Scene 수명과 게임별 전환/진행 트랜잭션 분리 |
| [IScene.h](../../TextRPG/Scene/IScene.h) | 공통 Scene 입력 결과에 StartGame/Continue가 포함 | 게임별 행동은 콘텐츠 결과로 유지하고 코어 계약에서 제거 |
| [Main.cpp](../../TextRPG/Main.cpp) | 프레임 루프와 게임 시작·복원·저장 정책을 함께 연결 | 코어의 프레임 절차와 앱의 게임 정책 hook을 구분 |

`SUIOption`은 실제 FDataScene 소비자가 있는 모델이며 단순 미사용 잔재가 아니다. 현재 bridge는 콘텐츠 연결기로 해석하면 성립하지만, 이를 공통 FUIManager로 취급하거나 그대로 코어에 이동하는 것은 목표 경계에 맞지 않는다. 비소유 포인터라는 사실도 컴파일 의존성과 역할 혼합을 없애지 않는다.

## 3. 목표 의존성

```text
TextRPG.exe ──→ ConsoleGameCore.lib
      └──────→ GameData.lib

GameDataPacker.exe ──→ GameData.lib  (일반 소비 경로, 구성 호환성 확인 후 연결)
Generator ──→ 생성 타입·데이터 ──→ GameData 빌드·dat 패킹
```

- `ConsoleGameCore.lib`는 TextRPG 소스, `GameData.lib`, 생성 테이블·Enum·현지화 키, InGameData/FGameSession을 include/link하지 않는다.
- `GameData.lib`는 ConsoleGameCore의 UI·Scene·프레임 관리에 의존하지 않는다. 정적 데이터 라이브러리는 게임의 실행 정책이나 진행 루트를 소유하지 않는다.
- 두 라이브러리의 연결·변환은 TextRPG가 담당한다. 예를 들어 ArtId 조회 결과를 표시 자료로 준비하고 공통 UI에 전달한다.
- GameData는 TextRPG 전용이므로 생성 테이블 변경에 따른 해당 라이브러리 재컴파일은 정상이다. 변경된 공개 헤더/PCH의 소비 범위도 정상적으로 무효화한다. 정적 라이브러리 생성만으로 전체 빌드 시간 단축을 보장하지 않는다.

## 4. 책임·소유권·실패 경계

| 대상 | 소유/결정 책임 | 입력과 출력 | 실패·수명 요구 |
|---|---|---|---|
| InputManager | 기기 상태·정규화된 전이 | 공급자 입력 → 프레임 상태/이벤트 | UI/Layer·게임 행동을 모르며 조회는 비소비 |
| 공통 프레임 실행부 | Input → Update → Render/Present → EndFrame 호출 순서 | 콘텐츠가 제공한 중립적인 프레임 hook | 수락과 완료를 구분, callback 중 삭제 금지, 출력 실패 뒤 경로 보존 |
| 공통 Scene 기반 | 일반 Scene 수명·busy·안전점 | 일반 Scene 계약과 전환 요청 | 첫 callback부터 unwind/정리까지 보호, 지연 취소·완료 단일 게시 |
| 런타임 Scene | Layer 목록·UITopLayer·입력 허용, 소유 UI 트리 | 입력 → 허용된 최상위 Layer | 하위 관통 금지, Manager에 Layer 최고값 복제 금지 |
| 공통 UI/root | 기하·포커스·캡처·제스처·렌더·중립 UI 이벤트 | 입력 → Activated 등과 안정 UI ID | 최초 virtual 조회·거부 인수 destructor까지 보호, 실패한 교체는 기존 표시 유지 |
| 공통 FUIManager | 필요한 경우 활성 UI 입력 대상의 비소유 연결 | 중립 입력/취소·detach 계약 | 구체 Scene/게임 Enum 없음, Scene 트리·진행·Layer를 별도 소유하지 않음 |
| GameData Store | 정적 테이블·자산 메모리·검증·조회 | 인증 패키지 → 검증된 정적 정의 | 실패한 Load는 기존 행/버퍼/참조 보존, 값의 단일 원본은 Excel |
| TextRPG 콘텐츠/세션 | 행동 해석·게임상태·전환/저장 정책 | UI ID + 게임 정의 → typed 게임 요청 | InGameData 단일 소유, 이전 UI 정리와 진행 교체의 결합 게시·파일 보존 |

기존 raw pointer를 무조건 shared_ptr로 바꾸거나 모든 요청을 임의 lambda queue로 옮기지 않는다. 새 중립 인터페이스는 기존 중립 계약으로 표현할 수 없는 실제 경계에만 최소로 추가한다. 표는 확정한 책임이며 구체 새 API 이름·메서드 서명은 구현 전 최소 계약 단계에서 결정한다.

## 5. FUIManager 결합 제거

### 5.1 데이터 모델과 행동 해석

- `SUIOption`의 ActionType·TargetSceneId 등 게임 의미는 FDataScene 등 콘텐츠 소유 모델로 옮긴다. 공유 UI Manager 헤더가 이 모델의 선언 위치가 되면 안 된다.
- 코어 버튼/선택 UI에는 표시 문구, 중립 ID, 활성 여부와 UI 이벤트만 전달한다. 게임 정의의 OptionId를 중립 ID로 대응할 수 있지만 코어는 그 ID의 의미나 생성 Enum을 해석하지 않는다.
- 클릭이 유효하게 확정되면 콘텐츠가 UI ID를 게임 선택지 정의와 매핑해 StartGame/Continue/Attack 등을 결정한다. UI 내부에서 HP·Gold를 수정하거나 콘텐츠 테이블을 조회하지 않는다.
- TextRPG의 네 슬롯/정렬/비활성 행동 규칙은 콘텐츠 조립과 데이터 검증에서 유지한다.

### 5.2 Scene 연결과 입력 권한

- 공통 FUIManager를 유지한다면 구체 FDataScene이 아닌 최소 중립 UI 입력 대상에 비소유 바인딩한다. 대상의 실제 Layer 허용 결정은 런타임 Scene이 수행한다.
- `GetBoundScene()`처럼 구체 콘텐츠 포인터를 반환하는 코어 API를 제거한다. 필요한 연결 identity와 detach 확인은 중립 대상/안정 토큰으로 표현한다. 콘텐츠용 조회가 필요하면 콘텐츠 연결기에 둔다.
- 중립 입력 대상은 게임 행동 Enum이나 FGameDataStore/InGameData를 노출하지 않는다. `IGameScene`으로 이름만 바꾸고 게임 명령 API를 유지하지 않는다.
- UIManager가 base root에 직접 입력을 보내 Scene의 최상위 Layer 정책을 우회하면 안 된다. base-root 조회가 남아도 입력 권한 판정에는 사용하지 않는다.
- 콘텐츠 callback의 등록·해제 수명은 해당 Scene/UI 소유 수명에 묶는다. ID/토큰은 실제 유효성을 검증하며 raw this 포인터를 파괴 후 호출하지 않는다. 같은 입력을 UIManager와 SceneManager가 중복 dispatch하지 않는다.
- 기존 bridge의 취소 예외 복구와 최종 detach를 보존한다. 취소 callback이 새로운 연결을 명시적으로 게시한 경우 이전 연결로 덮어쓰지 않는다. 재바인딩/교체/거부/예외 경로의 callback와 destructor를 모두 수명 보호 범위에 넣는다.

## 6. 프레임·Scene·진행 교체

- 프레임 순서는 Input → Update → Render/Present → EndFrame으로 유지한다. 코어는 프레임 구동과 일반 수명 안전점을 제공하고 TextRPG는 그 안전점에서 게임별 작업을 조정한다.
- 구체 Scene 생성·정의 조회·NewGame/Continue·typed 진행 후보는 콘텐츠가 책임진다. 코어는 InGameData의 레이아웃이나 저장 API를 알지 않는다.
- Scene 교체와 진행 교체는 동일 안전점의 결합 작업이어야 한다. 코어가 Scene을 독립 게시한 뒤 앱이 별도 다음 단계에서 진행을 교체해 불일치한 상태를 callback에 노출해서는 안 된다. 구현 전 좁은 전환 협력 계약과 실제 성공/실패 흐름을 먼저 확정·검증한다.
- 기존 첫 요청 우선·snapshot·다음 프레임 이월·재귀 guard, busy 취소 지연, 후보 UI 정리 후 진행 해제, 최초 GetId/Find부터 인수 정리까지의 guard를 유지한다.
- OnExit 취소 callback throw 뒤 framework flag/바인딩을 복구하고, 최종 파괴 뒤 연결을 해제한다. old destructor의 Quit는 후보 게시·Started·자동 저장을 차단한다. 이미 파괴한 old Scene을 복원했다고 주장하지 않는다.
- TakeStartResult 등 게임 완료 소비와 게시 후 NewGame 자동 저장·정상 Quit 저장·Continue 비저장 정책은 콘텐츠에 둔다. 루프를 코어로 이동하면서 이를 기본 코어 정책으로 만들지 않는다.

## 7. 소스·프로젝트·빌드 분리 기준

아래는 분리의 배치·빌드 기준이다. 실제 생성한 프로젝트와 경로는 §10을 따른다.

- `ConsoleGameCore/`: Input·Rendering·공통 UI·일반 Scene/Frame 코드 및 StaticLibrary 프로젝트.
- `GameData/`: 기존 Excel/Class/Data/Asset 원본·산출 경로를 보존하면서 전용 StaticLibrary 프로젝트와 런타임 코드를 배치한다. 물리 이동은 소비자 경로 조사 후 확정한다. Excel/txt/YAML을 C++ 코드로 컴파일하는 것이 아니다.
- `TextRPG/`: 구체 Scene/UI, 행동·세션·진행/저장 정책과 앱 조립.
- 코어 PCH/include 경로에 TextRPG 루트나 GameData/Class를 넣어 결합을 감추지 않는다. 표준/SDK·안정 인터페이스 PCH 정책과 일반 헤더 include 금지를 유지한다.
- 기존 게임/도구/테스트 소비자와 동일한 구성·플랫폼·CRT/ABI·define을 확인한다. 원본 CPP 중복 컴파일 대신 호환되는 일반 소비자는 ProjectReference로 연결하며, PCH/obj는 타깃·구성·아키텍처·분석별로 격리한다.
- 예외/매크로 치환·생성 헤더 부재 fixture는 고정된 제품 lib로 대체하면 검증 조건을 잃을 수 있다. 기존 원본 직접 참조의 특수 variant와 캐시를 유지한다. 일반 lib 연결 경로의 실행도 별도로 확인한다.
- Generator 선행 순서와 dat 패킹은 컴파일/링크와 구분한다. 공유 생성기를 중복 실행하거나 두 프로젝트가 같은 생성물/패키지를 경합 게시하지 않도록 한다.
- `.sln`·`.vcxproj`·filters·include·기존 runner를 같은 변경에서 갱신한다. 소스/시안/아트 원본을 임의 복구하지 않으며 승인 차단된 AGENTS 쓰기는 재시도하지 않는다.
- 출력은 기존 Out 규칙 아래 프로젝트별로 격리하고 기존 PCH·증분 Build를 재사용한다. 라이브러리 최초 빌드의 필요한 컴파일과 불필요한 Clean/Rebuild를 구분한다.

### 수용 시 빠뜨리면 안 되는 구분

- lib 파일 존재/링크 성공과 게임 독립성은 다르다. 코어 소비자의 include/link 입력을 제한한 실제 빌드·실행으로 확인한다. 단순 금지 문자열 검색만으로 인정하지 않는다.
- source-only 검토와 실제 lib 연결 앱 실행을 구분한다. 동결 소스의 관련 경계 독립 검토도 유지한다.
- 일반 lib 소비와 fault-injection/optional-generated-header 테스트의 의미를 모두 유지한다. 테스트를 줄이거나 assert를 삭제해 구조 변경을 통과시키지 않는다.
- 구조 분리 성공, warm 증분 재사용, 전체 작업 시간 단축은 서로 다른 주장이다. 측정하지 않은 속도 개선을 완료 효과로 쓰지 않는다.
