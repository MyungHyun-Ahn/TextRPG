# 기본 스탯·턴제 전투와 1차 플레이 사이클

> 상태: 1차 플레이 사이클의 로컬 구현·네 구성 증분 빌드/분석·실제 게임 검사·독립 소스 검토를 완료했다. 마을→전투필드→기본 공격→승패/귀환→재진입을 확인했다. 이전 검토 실패와 보완 증거는 보존한다. 커밋·푸시는 하지 않았다.

## 1. 확정 요구와 범위

사용자 목표는 마을 입장 → 전투필드 이동 → 플레이어 한 명과 몬스터 한 마리가 서로 기본 공격만 사용하는 턴제 전투다. 앞선 최소 사이클 목표에 따라 전투 종료 후 마을로 돌아와 다시 전투할 수 있게 한다.

- 원본 스탯: 힘·민첩·지력·운.
- 힘은 방어력, 민첩은 스피드, 운은 치명타 확률에 기여한다.
- 지력은 지력 계열 스킬의 높은 피해 계수로 가치를 준다. 별도 관통력·효과 적중·저항을 추가하지 않는다.
- 운은 피해량을 증가시키는 치명타 확률이다. 추가타·추가 행동으로 구현하지 않는다.
- 장비·원본 증가분 등을 모은 뒤 최종 기본 스탯과 파생 전투 스탯을 계산한다. 계산된 결과는 저장하지 않는다.
- 첫 구현은 이동·기본 공격·피해/사망·결과/귀환·현지화 전투 로그까지다.
- 상점·여관·보상/경험치 지급·장비 기능·스킬 습득/장착·아이템 사용·상태 이상은 구현하지 않는다.

## 2. 1차 동작 기준

```text
새 게임/기존 마을 진행
  → 마을: 이동만 활성
  → 전투필드: 몬스터 한 마리 준비
  → 기본 공격 선택: 양쪽의 한 라운드 진행
  → 계속 싸우거나 승리/패배 확정
  → 결과 확인 후 마을로 돌아가기
```

기존 정확히 네 슬롯/NoScroll 및 입력 release gate는 유지한다. 마을의 대화/상점/여관 등 기존 미구현 옵션을 활성화하지 않는다. 전투에서는 기본 공격만 사용하고, 귀환은 결과가 확정된 뒤에만 활성화한다. 스킬/아이템/방어를 동작하는 기능처럼 노출하지 않는다.

후술한 라운드 추첨·피해 식·회복은 이번 프로토타입을 실행하기 위한 **1차 기준안**이며 최종 밸런스의 사용자 확정으로 취급하지 않는다. 해당 수치/계수와 시나리오는 Excel에서 조정할 수 있게 한다.

- 매 라운드 시작에 현재 스피드의 양수 가중치로 선공을 추첨한다. 양쪽의 행동 기회는 각각 한 번이며 스피드는 추가 행동 횟수가 아니다.
- 첫 버전은 기본 공격 선택 한 번으로 선공/후공 순서의 라운드를 진행한다. 앞쪽 타격으로 전투가 끝나면 뒤쪽은 공격하지 않는다.
- 스피드가 같으면 동일 확률이며 라운드 경계에 같은 쪽이 연달아 행동할 수 있다.
- 기본 공격 피해는 기본 피해 + 각 원본 스탯의 계수 기여에서 방어력을 적용한다. 최소 피해·힘 방어 기여·민첩 스피드 기여·치명타 확률과 상한·피해 배율 등 조정값은 Excel 원본이다.
- 치명타는 해당 타격의 피해 배율이며 별도 타격/추가 턴을 만들지 않는다.
- 치명타 배율은 uint64 중간값으로 계산하고 남은 HP로 제한한 뒤 적용 피해를 uint32로 변환한다. 큰 정상 수치 조합이 축소 변환 때문에 전투를 멈추지 않게 한다.
- 최대 라운드는 최소 피해로 상대를 처치할 수 있는 예산 이상이어야 한다. 활성 상태를 복원할 때도 남은 라운드·남은 상대 HP가 이 예산을 만족하는지 검사한다.
- 양쪽 모두 같은 피해 처리 경로를 사용한다. 다른 점은 플레이어 입력과 몬스터 기본 공격 선택이다.
- 전투 종료 뒤 추가 공격을 거부하고 난수/HP/턴을 소모하지 않는다. 유효하지 않은 요청도 상태를 소모하지 않는다.
- 마을 복귀 시 회복은 초기 사이클을 반복 가능하게 하는 임시 데이터 정책으로 둔다. 사망 페널티·유료 회복·여관 기능을 추가한 뜻이 아니다.

## 3. 데이터 원본과 저장

정적 수치·계수·이름/아트·로그·이동 대상은 Excel이 유일한 원본이다. 생성 헤더/YAML은 실제 Generator로 재생성하고 직접 편집하지 않는다. 정적 Scene은 SceneId/SceneType/IsStartupScene 세 필드만 유지한다. 전투 상대/규칙은 전투 도메인 정의이며 정적 Scene에 현재 몬스터·HP·배치 필드를 넣지 않는다.

| 구분 | 소유/재생성 |
|---|---|
| 정의의 기본 스탯·기본 HP/피해·계수·텍스트/아트 키 | GameData의 Excel 정의 및 검증된 Store |
| 영구 증가분·현재 HP·현재 위치·진행 중 상대 HP/턴/결과·전투 RNG seed/count | 세션이 단독 소유하는 InGameData 원본 |
| 최종 기본 스탯·최종 방어/스피드/치명타 확률 등 | 현재 정의/원본에서 재계산; 저장하지 않는 계산 결과 |
| 포커스·선택·스크롤·렌더링 상태 | Scene/UI |

기존의 HP/공격/방어 StatBonuses는 과거 진행의 영구 원본 증가분이다. 이름이 같다고 새 파생 캐시로 오인해 지우지 않는다. 새 원본 필드는 호환 가능한 기본값/진행 검증과 함께 추가하고 기존 Save/Load 및 전용 키를 임의 덮어쓰지 않는다.

현재 생성 스키마는 3이며 새 기본 스탯 증가분/전투 원본은 since 3으로 도입한다. 기존 숫자 키 schema 2는 당시 여섯 루트 필드만 쓰는 독립 writer로 복원·HP/보너스/재화/컬렉션 보존을 확인했다. 기존 문자열 ID 읽기 경계도 유지한다. 전투 세 테이블은 완전한 client-visible 집합과 필수 필드·PK/FK·Scene 역할·몬스터 36×36 아트 계약을 생성기와 Store에서 검사한다.

기존 Quit 저장과 Continue를 유지한다. 진행 중 전투를 저장하면 상대·턴·결과·전투 난수 위치를 함께 복원해야 하며 seed/count만으로 전체 전투 복원을 가장하지 않는다. 파생 스탯은 로드 후 정의와 원본으로 다시 계산한다. 지원되지 않는 미래 상태는 명시적으로 거부한다. 행동별 자동 저장이나 비용/보상 트랜잭션을 새로 설계하지 않는다.

## 4. 런타임 경계

- GameData: 정적 정의·패키지 로드·숫자 키/참조/범위/완전한 테이블 집합 검증. UI나 TextRPG를 역참조하지 않는다.
- InGameData: 원본 진행과 직렬화. 플레이어 HP를 전투 객체에 별도 변경 가능 사본으로 중복 소유하지 않는다.
- Combat: 게임 측 콘텐츠 로직으로 행동 검증·스탯 계산·선공·피해/결과를 처리한다. 콘텐츠 독립 ConsoleGameCore에 이 게임의 규칙을 넣지 않는다.
- Session/SceneManager: 이동 후보 준비와 EndFrame의 Scene/진행 결합 게시. 준비/전환 실패 시 이전 Scene/진행을 보존한다.
- Scene/UI: 진행을 비소유 조회하며 입력을 행동 요청으로 전달한다. HP·몬스터·RNG 진행을 소유하지 않는다.

전투 FSelector는 별도 콘텐츠 스트림이다. 최초 한 번 생성한 seed와 raw count를 유지하며 로드/렌더/거부 요청에서 재시드하지 않는다. 실패 가능한 준비·할당·난수 처리는 후보에서 수행하고 성공한 행동 결과만 게시한다.

전투 로그는 행동/피해/치명타/종료의 구조화된 결과와 현지화 키로 표시한다. 게임 문구를 C++ 문자열 상수로 추가하지 않는다. 플레이어/몬스터 이름·HP·필요 아트는 현재 원본의 비소유 표시로 연결한다. 기존 사용자 BattleUiPreview와 FDataScene.h 아트 주석은 보호한다.

## 5. 이후 확정 확장 요구 — 이번에는 미구현

- 직업 없이 구매/드롭/가챠로 스킬 습득, 최대 네 개 장착.
- 레벨별 장착 코스트 합 제한. MP 같은 전투 자원과 혼동하지 않는다.
- 스킬별 고정 피해와 힘/민첩/지력/운의 혼합 계수. 지력 계열은 상대적으로 높은 지력 계수를 가질 수 있다.
- 자기 턴 기준 쿨타임. 사용 턴 차감·기절 중 경과 등 정확한 규칙은 해당 구현 시 확정한다.
- 침묵: 기본 행동/아이템 외 스킬 제한. 기절: 지정한 행동 기회 제한.
- 독/화상/출혈: 지정 시점의 지속 피해와 사망 판정. 중첩/갱신은 효과별 규칙으로 확장한다.
- 버프/디버프: 원본 효과를 모아 최종 스탯을 재계산한다. 반복 가감으로 누적 오차를 만들지 않는다.
- 아이템 사용도 유효 행동 확정 시 턴을 소비한다.
- 몬스터는 선택적 디버프 스킬과 공격 스킬 여러 개를 가지며 효과 처리와 행동 선택을 분리한다.
- 스킬마다 고유 현지화 로그를 지정한다. 임의 코드 실행기나 범용 스크립트 엔진은 선행 구현하지 않는다.

## 7. 실행 기록

v1의 실제 Debug/x64 게임에서 마을→기본 공격 전투→결과/귀환이 동작했고, 사용자 후속 승인으로 새 데이터의 프로젝트 등록 및 구조 검사17개를 완료했다. 이는 전체 호환/경계 수용 완료가 아니다.

독립 검토 v1은 기존 schema2 세이브의 새 필드 부재 처리, 최대 라운드 도달 시 미종료 상태, Store/Excel 수치 범위 불일치, 신규 수기 멤버 명명/Allman 및 생성 registry 행 길이 문제로 실패했다. 데이터 검토는 원본 CharacterDefinition과 일부 생성기 의존 입력 누락 때문에 complete=false도 보존한다. repair1에서 이 지적만 실제 RED/GREEN으로 보완하고, 다음 동결 입력에는 누락된 원본/생성기 계약을 포함한다. 최초 FAIL을 수정하거나 실행 통과로 소스/범위 결함을 대체하지 않는다.

증거는 소유 scratch `combat-phase1-77a0a983`의 `implementation/`, `final/`, `review/v1/`, `repair1/`에 구분한다. 네 구성 최종 검증·보완 후 독립 검토·수용 기록 전에는 완료로 표시하지 않는다. 문서 작성 체크는 플레이 가능한 기능 완료 표시가 아니다.

### 최종 로컬 수용

- v2 검토에서 생성기의 필수 scope/독립 FK/Scene·아트 역할 검사 누락과 큰 치명타의 조기 uint32 변환을 추가 발견했다. 두 번째 보완에 모아 실제 거부 전환·피해 경계 RED/GREEN과 필수 주석 규칙을 보완했다. 최초 FAIL/미완료/공급자 HTTP 400 기록은 그대로 남긴다.
- Debug/Release × x64/Win32의 solution Build 및 제품 분석이 경고0으로 통과했다. 네 구성의 일반/분석에서 Scene/UI 99, InGameData 214, Store 429 checkpoint group을 확인했다. 이를 단위 테스트 수로 합산하지 않는다.
- Debug/x64 Store 일반/분석은 기존 통과 증거를 재사용했다. 해당 CPP 변경은 한국어 주석 두 곳뿐이고, 변경된 C# 검증기는 정상 생성물 바이트를 바꾸지 않았다. 나머지 세 구성은 현재 후보로 실행했다. TextArt 헤더 부재 variant도 Debug/x64 일반/분석에서 통과했다.
- 실제 EXE는 네 구성 각각 일반 23 case, 전투 모드 2 case, 진행/저장 모드 5 case가 통과했다. 모드마다 중복되는 누락 패키지 거부 사례는 독립 기능 수로 부풀리지 않는다. 최종 EXE 해시와 검사 입력 해시를 대조했다. 소유 콘솔의 입력/버퍼 검사이며 수동 시각 인증은 아니다.
- 최종 Release Generator DLL과 의존성을 복사해 원본 DLL 해시 일치 상태에서 self-test·정적 생성물 check·진행 스키마 check를 통과했다. 조정자의 잘못된 YAML 출력 루트 인수는 소유권 검사로 거부됐고, 프로젝트에 선언된 Data 루트로 해당 check만 수정 실행했다. 제품 결함/추가 보완으로 세지 않는다.
- 최종 소스 검토는 v3의 변경 6경로 PASS와 바이트가 같은 이전 검토 49경로의 범위를 조합한 55경로다. 누락됐던 경로 결정 함수/PCH 및 관련 include 참조도 제공·검토했다. 전체를 새로 재검토했다고 주장하거나 이전 부정 판정을 PASS로 덮어쓰지 않는다.
- 실행/소스 범위는 `final/v3/execution-index.json`, `final/v3/source-composition.json`에, 각 보완은 `repair1/`, `repair2/`에 기록한다. 이후 문서 마감은 코드와 EXE를 다시 실행하지 않고 정체성/링크만 확인한다.
- 기존 `APP-D32-EMPTY-OUTPUT`의 과거 원인은 여전히 사용자 승인 보류다. 이번 Debug/Win32 검사 통과를 과거 원인 해결로 바꾸지 않는다. 스킬·아이템·상태 이상·보상은 미구현이며 밸런스 값은 여전히 프로토타입 기준이다.
